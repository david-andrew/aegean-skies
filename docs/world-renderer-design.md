## Requirements and first bound

500×400 km, existing archipelago unchanged, landable/walkable land, local 8 m collision /14 m render quality, mainland mountains near3000 m, flight to4000 m. No cloud, flight-physics or sea-look redesign. Keep sea inputs, chart and geography data coherent. Offline authored macro geography + deterministic detail must avoid a full-world player startup bake.

Dense source everywhere at8 m would require3.125 billion samples: 5.82GiB even at16bits/sample, before normals, masks, caches or browser overhead. Dense14 m render data requires1.020 billion samples:3.80GiB atRGBA8 alone. Therefore a world-sized resident fine grid is categorically incompatible with the web target. Sparse land helps but does not solve country-sized mainland storage. Resident memory and generated detail must follow the player; coarse whole-world data must remain bounded.

Provisional candidates (not yet selected):
1. Bounded cache of stitched quadtree tiles, shared fixed grid meshes, small whole-world macro pyramid and deterministic near-detail generation; preserves current renderer's strengths and exact legacy island data.
2. Nested geometry clipmap rings, coarse macro map plus near height cache; predictable draw count and memory, but integration must handle sparse islands, current error bounds and exact collision interpolation.
3. Fully baked sparse quadtree pyramid streamed from static hosting; lowest generation risk but likely excessive download for the entire landable world. Need quantify compression and request overhead.

No performance guarantee is made yet. Current-main native/browser baseline and backend capabilities must be measured; world-scale branch figures describe different code and are not today's baseline.

### Verified research, first pass

- **Geometry clipmaps (Losasso/Hoppe2004; GPU implementation2005):** viewer-centered nested grids, incremental toroidal updates and transition morphing bound working-set size independently of total area. Residual pyramids support compression and detail synthesis. Vertex-texture displacement avoids rebuilding vertex buffers. Strong candidate for predictable cost, but sparse sea areas and sharp legacy cliffs need explicit error/coverage tests. [Original author](https://hhoppe.com/proj/geomclipmap/), [GPU Gems chapter](https://developer.nvidia.com/gpugems/gpugems2/part-i-geometric-complexity/chapter-2-terrain-rendering-using-gpu-based-geometry).
- **CDLOD (Strugar):** quadtree selection of regular GPU grids rather than viewer-centered rings; suits uneven land distribution. The author supplies paper and implementation. Need read full seam/morph and streaming sections before choosing exact variant. [Author repository/paper](https://github.com/fstrugar/CDLOD).
- **Outerra:** published terrain algorithm visualization explicitly contrasts bilinear coarse elevation with procedural refinement. Good precedent for coarse authored shape plus synthesized detail, not evidence that arbitrary GPU noise automatically matches CPU physics. [Developer explanation](https://outerra.blogspot.com/2009/02/procedural-terrain-algorithm.html). Grass work separately shares canopy data between near grass and distant terrain shading, a useful representation principle; vegetation implementation is outside this task. [Developer grass article](https://outerra.blogspot.com/2012/05/procedural-grass-rendering.html).
- **Proland:** INRIA's project report identifies procedural landscape generation/rendering; its primary site was inaccessible through the research tool. Need retrieve papers and inspect cache/task graph and residual-tile semantics. [INRIA report](https://radar.inria.fr/rapportsactivite/RA2018/maverick/uid78.html).
- **Microsoft Flight Simulator2024:** official FAQ describes cloud streaming to reduce local client size. This trades install footprint for service bandwidth/cache; not directly applicable to an offline deterministic seed-based game on static GitHub Pages. Need still distinguish2020/2024 elevation, imagery, photogrammetry and local procedural placement in detailed sources. [Official FAQ](https://www.flightsimulator.com/microsoft-flight-simulator-2024-faq/).
- **Far Cry4/5:** Ubisoft's FC4 slides separate baked distant geometry/textures from near heightmaps; adaptive virtual texturing caches material/decal work. FC5's developer talk covers compute LOD, culling and stitching. Learn bounded material work and shared-grid selection, but its GPU-compute pipeline is not directly portable to this engine's WebGL path. Current game has simple terrain shading, so virtual texturing complexity needs a measured benefit before adoption. [FC4 developer slides](https://media.gdcvault.com/gdc2015/presentations/Chen_Ka_AdaptiveVirtualTexture.pdf), [FC5 developer talk](https://www.gdcvault.com/play/1025261/Terrain-Rendering-in-Far-Cry).
- **Unreal World Partition/HLOD and RVT:** spatial cell streaming and aggregated distant representations address object/world working sets; runtime virtual textures cache shading data. Neither alone establishes collision height or a deterministic world generator. Use the working-set principle; do not import engine-scale infrastructure without need. [Epic HLOD documentation](https://dev.epicgames.com/documentation/unreal-engine/world-partition---hierarchical-level-of-detail-in-unreal-engine), [Epic RVT documentation](https://dev.epicgames.com/documentation/unreal-engine/runtime-virtual-texturing-in-unreal-engine).
- **No Man's Sky:** Hello Games'2017 talk establishes procedural terrain generation as the topic, but the retrieved synopsis does not document exact storage/LOD/collision algorithms. No unverified implementation details assumed. [Developer talk](https://www.gdcvault.com/play/1024514/Continuous-World-Generation-in-No).
- **Horizon:** Guerrilla's deferred-texturing presentation is about foliage/alpha-tested geometry; do not mistake it for evidence of a specific heightfield architecture. Terrain and placement talks still to retrieve. [Developer article](https://www.guerrilla-games.com/read/adventures-with-deferred-texturing-in-horizon-forbidden-west).

Survey still incomplete: Star Citizen, Elite Dangerous, Kerbal Space Program2, Ghost of Tsushima, Just Cause, detailed Horizon terrain, chunked-LOD original source, modern HPG/SIGGRAPH terrain papers, distance-field shadows and far impostors. Explicitly investigate what public sources do NOT establish about collision/determinism instead of filling gaps with guesses.

### Engine source inspection (current local Sloppy)

`~/dev/slop-lang/docs/API.md`, `lib/game/gpu.jo`, `lib/game/gpubuffer.jo`, `lib/game/gpuarray.jo`, `lib/web/gfx.js`:

- Vertex `texel`/`sample_lod` are supported; current terrain already samples packed heights from textures. Regular displaced grids need no new graphics feature.
- Instancing exists, including persistent InstanceBuffer; the array overload uploads on each draw. Shared grid meshes plus persistent per-tile records can reduce draw submission, but measure batch size and visibility.
- GpuBuffer compute dispatch is native GPU only through Vulkan. OpenGL/WebGL fallback executes CPU code and copies shader-readable data to integer textures. Do not assume a compute-heavy FC5-style pipeline is portable.
- Important distinction: GpuArray expressions can use float render-target fragment passes on OpenGL ES/WebGL2. This is a different API from GpuBuffer compute, and may enable procedural synthesis without compute shaders; availability/readback and formats need probing.
- Web glue exposes glTexSubImage2D, glBufferSubData, drawElementsInstanced and glGetMaxTextureSize. Thus incremental uploads exist at the low-level API. Public texture-array abstraction and float-render-target capability/limits are not yet established. No measured per-frame upload budget yet.

### Architecture estimates and provisional recommendation

All numbers below are analytical budgets, not implementation measurements. Prefer candidate1 (paged quadtree heightfield with CPU-authoritative deterministic detail) for the first pilot, pending the missing timings. It best preserves current14m triangulation/edge tests and handles sparse sea. Retain clipmaps as an alternative if tile-selection/submission costs prove dominant. Reject fully baked fine whole-world data as the default web payload.

- Macro grid at500m:1001×80116-bit samples=1.53MiB raw; full pyramid about2.04MiB. At250m:2001×1601=6.11MiB plus pyramid≈8.15MiB. A sparse coastline/ridge/region vector description may beat these but must be measured and must produce coherent drainage and shore geometry. Do not choose resolution before checking ridge silhouettes at4000m.
- Example tile cache:128129² tiles,8bytes per height/material sample=16.25MiB GPU;64257²f32 collision/source tiles=16.13MiB CPU. A second staging/parent cache can double these costs. These are ceilings to test, not an assertion that total browser memory will fall: today's atlas is only3.91MiB. Need explicit allocations, release decoded file copies, and account for wasm linear-memory high-water marks.
- Clipmap example:10levels of255² samples at8bytes=4.96MiB GPU before staging, normals/other masks. With14m finest spacing and octave rings, reach exceeds the world extent. Approximate ring mesh work is around1million triangles if all ten levels are active; actual visibility and height-dependent fine-level activation determine cost. It is not automatically cheaper than current visible island patches.
- Current legacy render LOD consumes3.08MB compressed. Deriving bounded legacy14m tiles from preserved8m baked source may reclaim enough download for the macro world, while keeping the original erosion exactly. Need ship cheap precomputed bounds/coarse roots, quantify per-tile generation and avoid re-deriving the entire archipelago at startup. Rendering and collision must share the existing canonical triangle interpolation, not independently interpolated versions of the same source.
- Detail-generation pipeline: stable integer tile IDs + generator version + seed; quantize the CPU-authoritative heights once and upload them. Explicit ghost-border samples and deterministic arithmetic/order prevent seams. GPU-only decorative normals may vary slightly, but cannot change collision height. Erosion with nonlocal dependency cannot be independently recomputed per tile without compatible halos/boundaries; preserve legacy bake and bake new macro drainage offline or derive a locally evaluable deterministic model.
- Coarse roots always resident; current tiles stay visible until finer data and boundary parents are ready. Prioritize collision safety and lookahead along velocity before optional visual refinement. At200m/s a1km tile is traversed in5s; use this as a generation/prefetch bound, not a frame-time allowance. Player/nearby physical bodies pin collision tiles even outside the camera. Far NPCs query macro geography/routes rather than demanding fine caches everywhere.
- Geometry-as-data: persistent region/landmass IDs, coastline contours, mountain/ridge constraints and sea connectivity from the same macro field; reserve a mask containing the entire legacy archipelago plus seabed/coastal halo. Inside it use original coordinates, heights, source files, harbors and layout unchanged. Blend only outside the protected region. The reference map was inspected; broad peninsula/mainland shapes, long islands and uneven small-island clusters matter more than uniformly distributed circular peaks. Authoring the final shape is phase2, not done here.
- Curvature already exists: `src/render_space.jo` uses EARTH_RADIUS6371000 and a horizon-based far plane. From4000m the sea horizon is approximately225.8km; a3000m peak extends mutual visibility to approximately421.3km. Across500km, tangent-plane sag is roughly19.6km, so keep curved sea/terrain projections consistent and test mountain bounds/horizon culling. Do not introduce a second curvature transform. Preserve camera-relative rendering and inspect f32 precision for country-scale world positions before retaining today's vec3 storage everywhere.

Near walkability and bounded resident detail are feasible architectural goals. Equal frame time and browser memory well below today's are NOT established: the present terrain working set is already small, and baseline performance is reportedly dominated elsewhere. Avoid promising whole-game FPS gains from terrain work. The pilot must prove no regression while making costs independent of total land area.
