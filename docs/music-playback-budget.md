# Playback cost plan

The richer renderer is for listening review until it meets the game's frame budget.
Do not infer frame cost from sound quality or from an instruction count alone. The previous
profile of the dense march used 2.30 times the original renderer's instructions; the
instrument loop dominated. The follow-up is about 2.40 times the original on the same
passage. The receiver remains a small fraction of the cost. This is not yet cheap enough
to claim the frame-time requirement passes.

## First candidate: procedural note-body cache

Cache the expensive **modal bodies**, not the receiver output. Piano, plucked strings and
percussion repeatedly compute the same decaying modes. Preserve per-note expression,
release, short noise excitations and the room mix at playback time. Winds and bowed
instruments already use cheap analytic cycles and can stay live initially.

A bounded bank of 64 two-second mono bodies at 16 kHz and signed 16-bit precision costs
4 MiB. Bodies are generated by our own synthesizer, with no recorded input. Build the
most common percussion keys first, then the selected piece's common pitched notes. A
cache key includes instrument, pitch, an effort bin and the model-bank revision. Changes
to note duration do not require another body: release is a separate live gate. Longer
notes need a short quiet-tail model or another cached block, not a discontinuous loop.

An offline walk of the current note streams, with effort rounded to steps of 16, gives
these **onset cache-hit estimates**, not CPU savings or listening results:

| Piece | Distinct modal keys | 32-slot LRU hits | 64-slot LRU hits |
|---|---:|---:|---:|
| Adagietto | 148 | 42% | 55% |
| Magnetic Rag | 116 | 68% | 90% |
| El Choclo | 82 | 72% | 76% |
| Gladiators | 60 | 93% | 96% |
| Ikariotikos | 42 | 87% | 92% |
| Bethena | 172 | 52% | 78% |

High-hit percussion is the best bounded first experiment. Effort quantization can be
replaced with interpolation between adjacent cached bodies if listening exposes steps;
that doubles reads and can increase the working set. A miss must not build seconds of
audio inside one game frame. Use a capped incremental bake while a piece is selected,
a small ready-audio queue, and a temporary live-voice fallback. On browsers this must
work without assuming threads or SharedArrayBuffer. A thread can be an optional native
acceleration, not the only implementation.

Seeking indexes directly into a cached note body at its age; the existing score overlap
lookup remains. Keep the shared hall and reception state separate, so seek can reset the
hall and frequency/signal changes remain instantaneous. Cache hits must not alter which
random numbers the live texture consumes, or block partition will change the sound.

## Phrase caching, if note caching misses the budget

Pre-render 2–4 second dry programme blocks, indexed by piece and absolute block number,
with enough note/reverb pre-roll to join cleanly. An eight-second 16-bit mono rolling
cache is only 250 KiB; however it **does not reduce the work of a first sequential play**.
It amortizes repeated audition/seeking and repeat passages, and moves work away from
individual render deadlines. Full-track caching would consume about 14 MiB for the
longest piece alone and creates a significant load-time bake. Shipping pre-rendered
whole tracks would greatly increase the download; it is not the first choice.

A phrase key cannot simply hash pitches: expressive timing, dynamics and articulation
must match too. Reusing a supposedly identical phrase with a different cadence would
undo this task's musical improvements. Crossfading independently rendered chunks is not
a substitute for preserving note phase, overlap and release state.

## Acceptance before landing

1. Compare the cached output to the accepted live sound on attacks, sustained/tied notes,
   release tails, overlaps, tempo changes and arbitrary seeks. Bound cache memory and
   misses explicitly; keep deterministic block partition tests.
2. Profile the same dense passage and worst onset/seek blocks, including cache misses.
   On the quiet laptop, under its benchmark lock, compare p50/p95/p99 render cost and
   whole-game frame time against main. Test browser runtime and allocation behavior too.
3. Accept only if the actual frame-time gate passes. If note-body caching cannot reach
   it, measure phrase-cache reuse before building the larger system. Do not trade away
   the user-approved tone merely to report a lower instruction count.

This is a measured implementation plan, not an implemented cache or a performance claim.
